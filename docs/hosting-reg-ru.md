# Размещение на REG.RU Host-0

Сайт: React. Сервер: Python / Flask через Passenger. База: **MySQL 8, InnoDB, utf8mb4**. Node.js нужен только на вашем компьютере для сборки. На хостинге не запускайте npm, Vite или `flask run`.

Проверено по документации REG.RU 9 ноября 2026 года: [характеристики тарифов](https://www.reg.ru/hosting/reliable), [Flask на хостинге](https://help.reg.ru/support/hosting/php-asp-net-i-skripty/kak-ustanovit-flask-na-hosting). Инструкция рассчитана на **ispmanager**. Фактические пути и доступные интерпретаторы смотрите в панели своего аккаунта.

## Домены этого проекта

Основной адрес: **https://dancesrevolution.ru**. Дополнительные адреса `dancesrevolution.com`, `www.dancesrevolution.com` и `www.dancesrevolution.ru` перенаправляются на основной с кодом 301. Например, `https://dancesrevolution.com/news?page=2` должен перейти на `https://dancesrevolution.ru/news?page=2`.

Приложение, база MySQL, uploads и админка существуют в одном экземпляре. В ispmanager создаются две записи сайта с разными директориями: `.ru` обслуживает приложение, `.com` содержит только перенаправление. Не добавляйте `.com` как псевдоним работающего Python-сайта: приложение принимает основной домен из `SITE_URL`.

## 1. Собрать на компьютере

```sh
npm ci
npm run release
```

Команда создаёт `release/host0-ДАТА-ВРЕМЯ.zip`:

```text
application/    приватный код Python, настройки по умолчанию, HTML оболочки
public/         публичные ресурсы и Passenger для dancesrevolution.ru
redirect-com/   файл .htaccess для dancesrevolution.com
READ-ME.md      эта инструкция
```

Архив не содержит паролей, базы, заявок или загруженных через админку файлов. Видео `public/assets/hero-video.mp4` не хранится в Git: перед сборкой убедитесь, что оно есть на компьютере. Если его нет, посетителям будет показана заставка.

## 2. Подготовить услугу

1. В личном кабинете REG.RU откройте услугу **Host-0** и привяжите оба домена. IP сайта возьмите в данных именно этой услуги.
2. На текущих DNS-серверах каждой зоны добавьте или измените A-записи:

   | Зона | Имя | Тип | Значение |
   | --- | --- | --- | --- |
   | dancesrevolution.ru | @ | A | IP вашего Host-0 |
   | dancesrevolution.ru | www | A | тот же IP |
   | dancesrevolution.com | @ | A | тот же IP |
   | dancesrevolution.com | www | A | тот же IP |

   `@` означает корень домена; некоторые панели показывают полное доменное имя. Замените прежнюю адресную запись, если она уже существует. MX и TXT для действующей почты сохраните. Существующие AAAA-записи также должны вести на этот хостинг. [Инструкция REG.RU по привязке без смены DNS-серверов](https://help.reg.ru/support/hosting/privyazka-domena-k-hostingu/kak-privyazat-domen-k-hostingu).
3. В ispmanager → **Сайты → Создать сайт** создайте `dancesrevolution.ru`, псевдоним `www.dancesrevolution.ru`. Директория обычно `www/dancesrevolution.ru`. В «Дополнительных возможностях» включите **CGI-скрипты** и **Python**, выберите **Python 3.12 или 3.13**, если версия доступна в аккаунте. Проект требует Python 3.12+; старую версию из примера REG.RU выбирать нельзя.
4. Создайте второй сайт `dancesrevolution.com`, псевдоним `www.dancesrevolution.com`, отдельная директория обычно `www/dancesrevolution.com`. Python для него не нужен. Если записи сайтов уже созданы, отредактируйте их.
5. После обновления DNS выпустите SSL-сертификаты для обеих записей сайта: один покрывает `.ru` и `www` для `.ru`, второй — `.com` и его `www`. Сертификат `.com` нужен и при перенаправлении. Затем включите HTTP → HTTPS для основного `.ru`.
6. В **Базы данных → Создать** заведите одну **MySQL 8** базу и отдельного пользователя с доступом только к ней. Сохраните имя сервера, базы, пользователя и пароль.
7. Подключитесь по SSH. Выполните `cd ~`, затем `pwd`, чтобы узнать домашний каталог. Доступные интерпретаторы: `ls -la /opt/python/*/bin/python`.

## 3. Разместить файлы

Распакуйте архив на компьютере и загрузите **содержимое** папок по SFTP либо через файловый менеджер ispmanager:

| Папка в архиве | Каталог на хостинге |
| --- | --- |
| `application/` | `~/dance-revolution/` — вне `www` |
| `public/` | `~/www/dancesrevolution.ru/` |
| `redirect-com/` | `~/www/dancesrevolution.com/` |

`~` — домашняя директория вашего пользователя на хостинге. Используйте реальные корни сайтов из ispmanager, если они отличаются от таблицы. Не создавайте лишний уровень `public` внутри корня домена.

В корне домена не должно оставаться старого `index.html` или `index.php`, перехватывающего главную страницу. Перед заменой сохраните старый сайт отдельно. Скопируйте и скрытый файл `.htaccess` из архива.

В публичном `passenger_wsgi.py` проверьте `APP_ROOT` и `INTERPRETER`. По умолчанию они указывают на `~/dance-revolution` и `~/dance-venv/bin/python`. Python-код, `.env`, базы и uploads не кладите в публичный каталог: nginx может отдавать статические файлы до обработки `.htaccess`.

Публичный `.htaccess` направляет `www.dancesrevolution.ru` на основной адрес. Файл из `redirect-com/` направляет оба варианта `.com` на `.ru`, сохраняя путь и параметры запроса. Проверка сертификата по `/.well-known/acme-challenge/` исключена из этих правил.

Если на `.com` уже настроен редирект через ispmanager, используйте один способ. Настройка в панели: **Сайты → dancesrevolution.com → ⋮ → Настройка редиректов → Создать**, код `301`, путь `/`, URL `https://dancesrevolution.ru/`. Не задавайте такое перенаправление всех страниц для основного `.ru`: это создаст цикл. [Инструкция REG.RU](https://help.reg.ru/support/hosting/redirekty/redirekt-cherez-panel-upravleniya).

## 4. Установить Python-зависимости

Используйте фактический путь из списка доступных версий:

```sh
/opt/python/ВАША-ВЕРСИЯ/bin/python -m venv ~/dance-venv
source ~/dance-venv/bin/activate
cd ~/dance-revolution
python -m pip install --no-cache-dir -r requirements.lock
cp .env.example .env
chmod 600 .env
mkdir -p ~/dance-data
chmod 700 ~/dance-data
```

В `.env` заполните:

```dotenv
APP_ENV=production
SITE_URL=https://dancesrevolution.ru
DATA_DIR=/var/www/ВАШ-ЛОГИН/data/dance-data
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_DATABASE=имя_базы
MYSQL_USER=имя_пользователя
MYSQL_PASSWORD=пароль_базы
SMTP_HOST=сервер_из_настроек_почты
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USER=dance@revolution-msk.ru
SMTP_PASSWORD=пароль_почтового_ящика
SMTP_FROM=dance@revolution-msk.ru
```

В архиве `.env.example` уже содержит `APP_ENV=production` и `SITE_URL=https://dancesrevolution.ru`. Локальный `.env.local` на хостинг не переносите: он может перекрыть серверные настройки.

Путь `DATA_DIR` должен быть абсолютным. Если оставить его пустым, файлы будут храниться в приватной `~/dance-revolution/.data/`. Для SMTP с портом 587 задайте `SMTP_SECURITY=starttls`. Адрес сервера берите в настройках почты ящика `dance@revolution-msk.ru`: домены сайта не меняют его адрес и провайдера почты. Пароли с `#`, пробелами и другими специальными символами заключайте в кавычки по формату dotenv.

## 5. Перенести текущие настройки, новости и администратора

Для существующего проекта используйте **импорт**, а не создание пустого сайта. Актуальная локальная база после перехода на Python — `.data/site-python.sqlite`; именно в ней сохраняются новые правки и заявки. Остановите локальный сервер и обработчик писем, скопируйте всю `.data/`, включая файлы `-wal`/`-shm`, если они есть, и `uploads/`. Загрузите копию в непубличный `~/dance-import/`. SQLite читается согласованно; исходные данные не изменяются.

На хостинге:

```sh
cd ~/dance-revolution
~/dance-venv/bin/python -m backend.cli import-sqlite ~/dance-import/site-python.sqlite
```

Импорт переносит настройки, новости, хеши паролей, заявки с заметками и статусами, очередь уведомлений и файлы из соседнего `uploads/`. Отправленные письма остаются отправленными. Сессии не переносятся: потребуется войти заново. **Логин и пароль останутся прежними.** Команда отказывается писать в базу с существующими пользователями, публикациями или заявками. Повторно выполнять её после запуска сайта нельзя.

Если переход на Python ещё не выполнялся и актуальные данные находятся в старой Node-базе, укажите `~/dance-import/site.sqlite`. Команда поддерживает оба формата. Не импортируйте старую базу поверх новой и не используйте её вместо `site-python.sqlite` после редактирования сайта в новой админке.

Для совершенно нового сайта вместо импорта:

```sh
python -m backend.cli init-db
python -m backend.cli admin
```

Смена пароля: `python -m backend.cli admin --reset`. Пароль вводится скрыто. Общего пароля администратора нет.

## 6. Настроить уведомления

Заявка и два уведомления сохраняются одной транзакцией. Форма сообщает об успешной отправке только после записи в базу. SMTP работает из cron, отдельно от ответа посетителю.

В ispmanager добавьте задачу **каждую минуту**:

```sh
cd /var/www/ВАШ-ЛОГИН/data/dance-revolution && /var/www/ВАШ-ЛОГИН/data/dance-venv/bin/python -m backend.cli send-mail
```

Задача отправляет до 20 писем за запуск, автоматически повторяет временные ошибки до 8 попыток. Состояние писем видно в карточке заявки. Пока SMTP не настроен, заявки всё равно доступны в админке, письма остаются в очереди. После исправления почтовых настроек окончательно неудачные письма можно вернуть в очередь командой `python -m backend.cli retry-mail`.

SMTP не гарантирует строго однократную доставку: при обрыве соединения после приёма письма почтовым сервером возможен повтор. Номер заявки при этом остаётся прежним, новая заявка не создаётся.

Раз в день добавьте очистку истёкших сессий и лимитов запросов:

```sh
cd /var/www/ВАШ-ЛОГИН/data/dance-revolution && /var/www/ВАШ-ЛОГИН/data/dance-venv/bin/python -m backend.cli cleanup
```

## 7. Запустить и проверить

Создайте пустой `.restart-app` в **публичном корне домена** — REG.RU перезапустит Passenger и удалит этот файл автоматически.

Проверьте `https://dancesrevolution.ru/health`, главную, `/news`, `/privacy`, `/consent`, `/admin/applications`, загрузку фотографий и положения. Админка: **https://dancesrevolution.ru/admin/**, логин и пароль после импорта прежние. Отправьте одну тестовую заявку: она должна появиться в админке, а после cron — прийти на обе почты. Проверьте, что `/.env`, `/backend/app.py`, `/site.sqlite` недоступны посетителю. Реальное подключение к почте и базе проверяется уже с реквизитами вашего хостинга.

Проверьте редиректы после установки SSL:

```sh
curl -I 'https://dancesrevolution.com/news?page=2'
curl -I 'https://www.dancesrevolution.com/news?page=2'
curl -I 'https://www.dancesrevolution.ru/news?page=2'
```

Ожидается код `301` и `Location: https://dancesrevolution.ru/news?page=2`. На основном `https://dancesrevolution.ru/news?page=2` не должно быть перехода на тот же URL. В Windows используйте `curl.exe`. Если вместо редиректа вы получаете `400`, запрос альтернативного домена дошёл до Python: проверьте отдельную запись `.com`, директории и загрузку скрытых `.htaccess`. Если правила Apache не применяются в конфигурации вашего аккаунта, задайте редирект в ispmanager или запросите настройку у поддержки REG.RU.

## Обновление и резервные копии

Перед обновлением сохраните дамп MySQL и весь `DATA_DIR/uploads/`. В панели можно создать экспорт базы; пароли не передавайте в аргументах команд. Для согласованной копии временно остановите изменения в админке и приём заявок либо используйте резервное копирование хостинга с согласованным снимком данных.

Обновляйте `backend`, `shared`, HTML оболочки в приватном приложении и публичные `assets`, `bundles`, `docs`. **Сохраняйте `.env`, базу MySQL и `DATA_DIR`.** Не удаляйте папку загрузок и не запускайте импорт повторно. При изменении зависимостей обновите их из `requirements.lock`, затем создайте `.restart-app`.

Текущая версия использует миграцию схемы №1; `init-db` не удаляет существующие строки. Будущие изменения схемы должны поставляться отдельными миграциями, а не пересозданием базы. Локальная SQLite используется только для разработки и тестов: в production сервер требует MySQL.
